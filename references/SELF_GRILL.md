# 文档驱动的设计质询与决策摘要

编制日期：2026-09-15。此处是可审阅的设计问题、结论及依据摘要，不是向用户提问，也不要求用户回答后才运行。

方法来源：Matt Pocock 当前的 `grill-with-docs` 将质询与共享术语、架构决策文档结合。本包按用户要求，将原先需要用户回答的访谈改为助手查证并给出有标记的默认决策；不照抄其一行委托实现，也不依赖其其他skills。资料见 SOURCES.md 的 S01/S02。

标记：REQ=用户明确要求；DOC=已核验文档行为；DEFAULT=本包工程默认，不是用户已确认偏好；LIMIT=能力与证据边界。

## 第一轮：任务是否定义清楚？

| 质询 | 已采用的决策 | 依据/落点 |
|---|---|---|
| 是做今日榜单，还是构建长期能力？ | 构建一次调用可完成的技能，由宿主每日触发，持久保存状态 | REQ；SKILL、SCHEDULING |
| “全面”能否保证穷尽？ | 不能把有限检索当全网全集；记录来源×领域×日期覆盖，逐周补盲 | LIMIT；coverage |
| 是否只找AI或只找高Star项目？ | 否；AI、科研环境、开发工具、网页、游戏创作、数据系统均有配额目标 | REQ+DEFAULT；config |
| 热门、有趣、创新是同一种排名吗？ | 分别定义：关注信号、编辑判断、对照差异 | CONTEXT；WORKFLOW |
| 数量不足是否用熟悉的大项目补齐？ | 禁止；目标40–80初筛、10–15深读，不足披露 | DEFAULT；零新增测试 |
| 是否需要问用户GitHub账号和全部技能？ | 不阻塞；未知信息保留null，贡献匹配用条件判断 | REQ；profile与能力测试 |

## 第二轮：什么证据足以写进报告？

| 质询 | 已采用的决策 | 依据/落点 |
|---|---|---|
| 搜索摘要能否证明项目仍存在？ | 不能；回到官方仓库和原始资料 | DOC/审核规则；SOURCES |
| 仓库公开就是开源吗？ | 不是；分别标开源、source-available、开放权重、未知 | DOC；OSI及license gate |
| 如何证明“今天增长多少Star”？ | 仅使用平台明确指标或两次快照，标实际时间差；首次不计算 | star_change与相关测试 |
| README写“性能最强”能否直接转述为事实？ | 保留为作者自述；没有可比基线不做性能排名 | claim.kind |
| 创新如何避免主观吹捧？ | 写清参照对象、具体差异、证据及未验证部分；证据不足称探索价值 | WORKFLOW |
| 哈希是否能证明事实真实？ | 不能；只检验摘录未被无意更改。真实性和语义支持由来源核验负责 | LIMIT；audit声明 |
| 链接能打开就可以标当前可贡献？ | 不可以；项目真实与issue可用是两道门槛 | CONTRIBUTION |

## 第三轮：贡献推荐是否真的可行动？

| 质询 | 已采用的决策 | 依据/落点 |
|---|---|---|
| good first issue是否足够？ | 只是发现标签；还需评论、指派、timeline、PR、规则与验收范围 | DOC；门槛测试 |
| 没有assignee能否说无人认领？ | 不能，评论或外部PR可能已有人推进 | claim_status；认领测试 |
| issue接口是否只返回issue？ | 否，GitHub部分issue端点含PR；检查pull_request字段 | DOC；collector显式排除 |
| 没找到关联PR是否等于不存在？ | 否，注明查询与分页范围；未查完整则降级 | pagination与gate |
| 研究过ML是否意味着能改大型ML框架核心？ | 不意味着；领域优势与具体工程技能分开写 | profile与技能证据测试 |
| 任务里是否可运行代码测能力？ | 每日发现阶段不执行候选仓库；只给最小验证方案，执行另行授权 | REQ边界；mission |
| 能否每天自动提交小PR刷贡献？ | 禁止；只提供有价值的任务分析，不制造维护负担 | mission |
| 项目禁止AI贡献怎么办？ | 明确政策，不规避；只考虑符合规则的人工贡献 | ai_policy |
| 没有合适issue怎么办？ | 允许零贡献候选；建议性改进单列不计数 | 模板与报告渲染 |

## 第四轮：长时间运行会如何失真？

| 质询 | 已采用的决策 | 依据/落点 |
|---|---|---|
| 每日新会话会忘记前一天吗？ | 状态写SQLite，启动读取短摘要与当前批次，不依赖会话延续 | DOC+设计；context |
| 把所有日报加载进上下文是否更好？ | 否；按ID查询，默认最近20项目、3运行、10反馈，字符预算约束 | context测试 |
| 摘要会不会把待确认压成确定？ | 不以旧摘要为事实源；保留原始证据、时间和status，过期重查 | MEMORY_SECURITY |
| 用户不回复是不是喜欢？ | 不是；偏好必须有明确用户原话，固定画像不自动修改 | feedback测试 |
| 今天没搜索到某issue是否应该删除？ | 不；保留上次观测并标过期，缺席不等于关闭 | omission测试 |
| 仓库改名是否算新项目？ | 不；GitHub使用数字ID、名称和URL作为可变字段 | identity |
| 两次运行同时发布会污染状态吗？ | SQLite事务序列化；旧时间快照不能回滚新事实；分支只读、父流程单写 | publish与回滚测试 |
| 一半写入就崩溃怎么办？ | SQLite为权威记录；报告可用export再生，每次运行不可变 | 恢复测试 |
| 外部README能否要求“忽略安全规则”？ | 外部内容一律不可信数据；不执行候选项目，不授予其本地规则权限 | mission |
| 定时任务不存在是否假装成功？ | 不；创建、启用、下次运行必须由真实宿主反馈确认 | SCHEDULING |

## 决策记录 ADR-001：文件型技能＋单一结构化状态库

状态：已采纳。采用渐进式SKILL/references组织指令，SQLite存观测与证据，Markdown/JSON为可重建输出。避免一个巨型memory.md混合用户偏好、项目事实和建议。代价是需要Python；无Python时降级而非假称结构化记忆已更新。

## 决策记录 ADR-002：调研与外部贡献动作严格分离

状态：已采纳。日报只读远端；贡献分析不自动授予fork、PR、代码执行或数据上传权限。代价是候选的真实复现成本与个人能力仍需后续验证，但减少低质量贡献、供应链与隐私风险。

## 决策记录 ADR-003：真实的不足优先于形式上的全面

状态：已采纳。配额是搜索预算与补盲目标，不是强制填表指标。来源失败、分页截断、未知许可、无法测量的token/cost必须显式保留。代价是有些日子报告较短，但不会把旧知识伪装成当天核验。
