# 简历与面试展示

## 可直接使用的项目描述

**Open Source Radar｜基于证据的开源项目发现与贡献机会分析工具**

技术栈：Python、SQLite、GitHub REST API、Codex Skill、GitHub Actions

- 构建开源项目调研与贡献机会核验流程，将来源、观测时间、原始摘录和 SHA-256 组织为结构化证据，支持中文 Markdown 日报、JSON 数据和 SQLite 本地记忆。
- 实现 issue 四级状态判定，结合认领记录、关联 PR、贡献规则与 24 小时证据时效筛选待复核机会，区分事实、作者主张和分析建议。
- 设计基于不可变项目 ID 的增量观测与事务化发布，支持幂等写入、旧快照防回滚和报告恢复；以 60 项离线测试及双次观测演示验证核心流程，并配置 Windows/Linux CI。

上述描述基于仓库实现与测试，不包含未测量的效率提升、用户规模、线上准确率或贡献成功率。个人角色、开发周期和是否使用 AI 辅助，应按实际参与情况填写和说明。

## 三分钟演示顺序

1. **问题（30 秒）**：热门项目发现之后，还需要处理 issue 占用、证据过期和跨会话遗忘。
2. **演示（60 秒）**：运行 `python -B examples/demo.py --output .demo-output`；打开 `summary.json` 和第二次日报，展示 Star +4、状态从待复核转为进行中、两次观测对应一个项目。
3. **设计（60 秒）**：展示架构图，解释 Agent 语义审阅与 Python 确定性校验的分工、数据库先提交与文件可恢复的取舍。
4. **验证与边界（30 秒）**：查看 CI 与测试，说明合成演示没有网络请求，哈希不能证明事实真实性。

若演示目录已存在且非空，选择新的目录名；不要为了演示清空个人运行数据。

## 面试可深入讨论的问题

| 问题 | 可结合源码解释的要点 |
| --- | --- |
| 为什么用 SQLite？ | 本地事务、唯一约束、历史查询、无服务部署；尚未验证多进程高并发 |
| 怎么保证重复运行不污染历史？ | run 身份、序列化内容一致性、不可变发布、观测复合主键 |
| 报告写到一半崩溃怎么办？ | 先提交数据库，再原子导出；从存储的报告、payload 和 manifest 恢复 |
| 为什么不自动认领 issue？ | API 无法证明不存在隐藏工作；明确区分值得复核与可直接行动 |
| 下一步怎么评价实际效果？ | 以人工复核集测误判率、证据完整率和过期状态漏检率；这些指标目前未测 |
